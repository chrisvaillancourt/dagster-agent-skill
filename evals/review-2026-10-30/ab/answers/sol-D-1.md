### Q2
Only assets included in the `dg.Definitions(...)` returned by the `@dg.definitions` function are loaded from that module; a module-level `@dg.asset` is omitted unless explicitly included. There is **no warning** about the omitted asset: the decorated definitions function takes precedence over module-level auto-discovery ([1.13.28 implementation](https://github.com/dagster-io/dagster/blob/1.13.28/python_modules/dagster/dagster/components/core/defs_module.py)).

### Q6
The root `dg` CLI callback sets `DAGSTER_IS_DEV_CLI="1"` for all normal subcommand executions, including `dg check defs`, `dg list defs`, `dg launch`, `dg dev`, and the `scaffold`, `utils`, `api`, `labs`, and `plus` command families—not just development-server commands ([implementation](https://github.com/dagster-io/dagster/blob/1.13.28/python_modules/libraries/dagster-dg-cli/dagster_dg_cli/cli/__init__.py)). Consequently, CI validation takes that conditional branch, while production loading without the variable takes the other branch. `dg check defs` additionally sets `DAGSTER_IS_DEFS_VALIDATION_CLI="1"`; use a separate deployment-environment variable rather than treating either flag as a production detector.

### Q11
With default `dg.DailyPartitionsDefinition` settings—midnight boundaries, UTC, and `end_offset=0`—the tick runs partition **`2024-05-19`**, the latest completed daily window. The schedule selects the latest available partition at the **scheduled tick time**, not necessarily the tick’s calendar date ([implementation](https://github.com/dagster-io/dagster/blob/1.13.28/python_modules/dagster/dagster/_core/definitions/partitions/partitioned_schedule.py)). Partition timezone, boundary offsets, `end_offset`, start/end bounds, and exclusions can change the result or cause a skip; for example, `end_offset=1` selects `2024-05-20`, while a 02:00 daily boundary with `end_offset=0` selects `2024-05-18` at 01:30. The schedule’s `hour_of_day` and `minute_of_hour` control when it fires, not the partition boundaries.

### Q28
`dg.materialize_to_memory` rejects the supplied `io_manager` with `DagsterInvariantViolationError`, because it forces in-memory IO managers ([API implementation](https://github.com/dagster-io/dagster/blob/1.13.28/python_modules/dagster/dagster/_core/definitions/materialize.py)). Removing that resource exposes a second problem: `[down]` does not define or supply the input asset `up`; `dg.materialize_to_memory([up, down])` computes and passes its value. To use filesystem-backed inputs, use `dg.materialize` with the appropriate upstream asset/source definition and IO manager. If `down` instead uses `@dg.asset(deps=[up])` **without an `up` function parameter**, the dependency is ordering/lineage-only, so `dg.materialize_to_memory([down])` succeeds without including or loading `up`, but supplying the IO manager remains invalid.

### Q33
In run-config YAML, use the enum **member name**, not its Python value: for `Color.RED = "red"`, write `ops: {my_asset: {config: {color: RED, pet: {cat: {meows: 10}}}}}`. The discriminated union uses a one-key selector such as `pet: {cat: {meows: 10}}`, not `pet: {pet_type: cat, meows: 10}`. Unknown keys in ordinary `dg.Config` run-config schemas raise `DagsterInvalidConfigError`; use `dg.PermissiveConfig` where extra keys should be accepted ([official configuration guide](https://docs.dagster.io/guides/operate/configuration/advanced-config-types)).

### Q45
These are **organization settings**, not deployment settings: set `max_concurrent_runs_per_branch_deployment: 5` and `max_concurrent_branch_deployment_runs: 100`. Retrieve the existing YAML with `uv run dg api organization settings get`, preserve its other settings while editing, and apply it with `uv run dg api organization settings set org-settings.yaml`; this requires **Organization Admin** permissions. Both limits apply simultaneously, and excess runs remain queued. The documented global maximum is 500 on Hybrid but 50 on Serverless, so Serverless needs a Support-approved increase to reach 100 ([official guide](https://docs.dagster.io/deployment/dagster-plus/deploying-code/branch-deployments/branch-deployment-concurrency)).

### Q52
Without stream `object` or metadata overrides, `public.accounts` produces **`dg.AssetKey(["target", "public", "accounts"])`**, with upstream dependency **`dg.AssetKey(["public", "accounts"])`** ([1.13.28 translator](https://github.com/dagster-io/dagster/blob/1.13.28/python_modules/libraries/dagster-sling/dagster_sling/dagster_sling_translator.py)). ### Q57
By default, a Dagster-triggered sync sets the connector’s Fivetran `schedule_type` to `"manual"`, disabling its automatic Fivetran schedule rather than merely skipping one occurrence. Set `FivetranWorkspace(disable_schedule_on_trigger=False, ...)` to leave the existing schedule unchanged; this does not re-enable an already-manual connector. The other setting is `retry_on_reschedule`, defaulting to `True`: Fivetran rescheduling causes `dg.RetryRequested` with a delay, whereas `False` keeps polling in the current Dagster step ([official guide](https://docs.dagster.io/integrations/libraries/fivetran/fivetran-pythonic)).
