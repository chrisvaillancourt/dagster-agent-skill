### Q4
The docstring example is invalid for a dataclass: `DefsStateConfigArgs.local_filesystem()` returns a mutable Pydantic model, so class creation raises `ValueError: mutable default ... is not allowed: use default_factory`, preventing commands that import the component from loading it. Import `field` from `dataclasses` and use `defs_state: ResolvedDefsStateConfig = field(default_factory=DefsStateConfigArgs.local_filesystem)`. This creates a separate configuration object for each component instance.

### Q9
No, not with default backfill settings: in 1.13.28, `dg launch --partition-range` requires every selected asset to have `backfill_policy=dg.BackfillPolicy.single_run()`. It executes the inclusive range in one run, rather than submitting one run per partition. The asset must process that range using `context.partition_keys` or `context.partition_time_window`, with range-aware storage instead of assuming `context.partition_key`. Otherwise, launch each partition with `uv run dg launch --assets my_asset --partition <date>`, or submit a backfill through the UI with a running daemon.

### Q13
`context.definition_metadata` contains metadata explicitly declared on the downstream `AssetIn` or `In`, not the upstream asset's metadata. Read the upstream table name from `context.upstream_output.definition_metadata["table_name"]`, which contains definition-time metadata from the upstream asset or output. In `load_input`, `context.upstream_output.output_metadata` emits a warning and returns `{}`; it does not expose metadata reported through `MaterializeResult`. Retrieve that metadata from materialization events through `context.instance.get_latest_materialization_event(context.asset_key)`, with appropriate partition/run filtering when “latest” would select the wrong event.

### Q22
Add a `dg.AutomationConditionSensorDefinition(name="custom_automation", target=dg.AssetSelection.assets(my_asset), use_user_code_server=True)` to your definitions, enable it through the UI or `default_status=dg.DefaultSensorStatus.RUNNING`, and run the daemon. Custom conditions are not serializable for daemon-side evaluation, so the default automation sensor cannot evaluate them; your `evaluate()` must return a `dg.AutomationResult`, not a Boolean. User-code-server evaluation is beta, limits each sensor to 500 targeted assets/checks, and runs within the sensor evaluation timeout. It does not support job automation conditions through `asset_job_keys`.

### Q31
Attach the new policy with `@dg.asset(freshness_policy=dg.FreshnessPolicy.time_window(fail_window=timedelta(hours=24)))` and run the daemon against your local instance, for example through `uv run dg dev`. In 1.13.28, freshness evaluation is enabled by default, so no additional `dagster.yaml` configuration, freshness sensor, or schedule is required. The policy monitors freshness but does not materialize the asset; triggering materializations remains a separate concern. The old class is now deprecated `LegacyFreshnessPolicy`, also available as `dagster.deprecated.FreshnessPolicy`, and is not interchangeable with the new `freshness_policy=` API.

### Q35
The default is `QueuedRunCoordinator`, not the immediate-launch `DefaultRunCoordinator`. The sensor submits all 25 runs to the queue, and the run queue daemon admits up to 10 in-progress runs by default, leaving the remainder queued until slots become available. With no other runs or limits, that means 10 running and 15 waiting once the first batch starts; the default dequeue interval is five seconds. Without a running daemon they remain queued, and `concurrency.runs.max_concurrent_runs` controls the limit.

### Q43
Configure `DAGSTER_CLOUD_ORGANIZATION`, the CI secret `DAGSTER_CLOUD_API_TOKEN`, and a fresh `DAGSTER_BUILD_STATEDIR`, preserving that state directory across stages. For a full Hybrid deployment, run `uv run dg plus deploy start --deployment=prod --deployment-type=full --target-path=.`, then `uv run dg plus deploy build-and-push --agent-type=hybrid`, then `uv run dg plus deploy finish`. `finish` updates the code locations using the image recorded by the earlier stages. Plain `uv run dg plus deploy` instead starts the entire workflow again, clearing the existing session state and rebuilding/pushing another image before deploying, rather than merely finishing the staged deployment.

### Q48
`external_asset_from_spec` and `external_assets_from_specs` were removed; pass `dg.AssetSpec` objects directly to `dg.Definitions(assets=[...])`. `dg.SourceAsset` and `AssetsDefinition.to_source_asset(s)` still exist in 1.13.28 but are deprecated, so use `dg.AssetSpec`, optionally with `.with_io_manager_key(...)` for downstream loading. Older `deps=dg.AssetKey("upstream")` syntax also fails; use an iterable such as `deps=[dg.AssetKey("upstream")]`. For observable source assets, `auto_observe_interval_minutes` no longer schedules observations and is silently ignored by the 1.13.28 decorator; configure `automation_condition=` with an enabled automation sensor, or explicitly schedule/request observations.

### Q54
In `defs.yaml`, use `type: dagster_powerbi.PowerBIWorkspaceComponent` and set `attributes.enable_semantic_model_refresh: true` alongside the `workspace` configuration. The component generates materializable semantic-model assets that trigger and poll Power BI refreshes, without Python wrappers. To enable only selected models, supply their names as a list, such as `enable_semantic_model_refresh: [sales_model]`. Because the component is state-backed, populate its workspace state with `uv run dg utils refresh-defs-state`, or let `uv run dg dev` refresh it locally.
