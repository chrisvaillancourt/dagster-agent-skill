### Q13
`context.definition_metadata` contains metadata explicitly assigned to the downstream input through `AssetIn(metadata=...)` or `In(metadata=...)`; `context.upstream_output.definition_metadata` contains the upstream asset/output definition metadata, so that is where a static table name belongs. Despite its name, `context.upstream_output.output_metadata` does **not** expose upstream runtime metadata inside `load_input`: in 1.13.28 it warns and returns `{}`. Retrieve `MaterializeResult(metadata=...)` values from stored materialization events—for example, `context.instance.get_latest_materialization_event(context.asset_key).asset_materialization.metadata`, whose values are `MetadataValue` objects—but filter by partition/run when “latest” might select the wrong event. See the [I/O context reference](https://docs.dagster.io/api/dagster/io-managers).

### Q22
Register a `dg.AutomationConditionSensorDefinition("custom_automation", target=..., use_user_code_server=True)` in `Definitions(sensors=[...])`, and enable it through the UI or `default_status=dg.DefaultSensorStatus.RUNNING`. Ordinary custom Python subclasses cannot be reconstructed by daemon-side evaluation; `use_user_code_server=True` evaluates them where your Python code is available, with `evaluate()` returning `dg.AutomationResult(context=context, true_subset=...)`. This execution mode is experimental/beta, supports at most 500 selected assets/checks per sensor, does not support targeting asset jobs, and requires the daemon, sensor-based automation (`auto_materialize.use_sensors`, true by default), and evaluation within the sensor timeout. See [arbitrary Python automation conditions](https://docs.dagster.io/guides/automate/declarative-automation/customizing-automation-conditions/arbitrary-python-automation-conditions).

### Q31
Attach `dg.FreshnessPolicy.time_window(fail_window=timedelta(hours=24))` with the asset’s `freshness_policy=` argument and run `uv run dg dev` or `uv run dagster-daemon run` against the instance. In 1.13.28 the freshness daemon is enabled by default, so no sensor, schedule, or explicit `freshness: {enabled: true}` configuration is required unless freshness was disabled. The policy monitors freshness; it does not materialize the asset, so execution automation remains separate. The old class became deprecated `LegacyFreshnessPolicy`—also accessible as `dagster.deprecated.FreshnessPolicy`—and is not the new `dg.FreshnessPolicy`; see the [1.12 upgrade notes](https://docs.dagster.io/migration/upgrading#upgrading-to-1120).

### Q35
The effective coordinator is `QueuedRunCoordinator`, **not** `DefaultRunCoordinator`, even without a `run_coordinator:` section; its default `max_concurrent_runs` is **10** in 1.13.28. The 25 sensor runs enter the queue, and the run-queue daemon launches them as capacity permits: with no other active runs and sufficiently long-running work, up to 10 run concurrently while 15 wait. Completed runs free slots; without a functioning run-queue daemon, the queued runs do not launch. These defaults are defined in [`InstanceRef`](https://github.com/dagster-io/dagster/blob/1.13.28/python_modules/dagster/dagster/_core/instance/ref.py) and [`QueuedRunCoordinator`](https://github.com/dagster-io/dagster/blob/1.13.28/python_modules/dagster/dagster/_core/run_coordinator/queued_run_coordinator.py).

### Q43
For a full Hybrid deployment, run `uv run dg plus deploy start --deployment=prod --deployment-type=full --yes`, then `uv run dg plus deploy build-and-push --agent-type=hybrid`, then **`uv run dg plus deploy finish`**; use the Serverless build options when appropriate. Provide `DAGSTER_CLOUD_ORGANIZATION` and `DAGSTER_CLOUD_API_TOKEN`, and preserve the same `DAGSTER_BUILD_STATEDIR` contents across CI stages; if CI builds/pushes the image itself, record it with `uv run dg plus deploy set-build-output --location-name=LOCATION --image-tag=TAG` instead of `build-and-push`. Bare `uv run dg plus deploy` runs the whole workflow again: it initializes a new session, discards the previous session state, rebuilds/pushes, and then updates locations—it does not merely finish your existing session. See the [deploy command implementation](https://github.com/dagster-io/dagster/blob/1.13.28/python_modules/libraries/dagster-dg-cli/dagster_dg_cli/cli/plus/deploy/commands.py).

### Q48
`external_asset_from_spec` and `external_assets_from_specs` were removed in 1.13; represent non-Dagster-produced assets with `dg.AssetSpec(...)` directly in `dg.Definitions(assets=[...])`, without converting the specs. Older code using `Definitions.get_all_asset_specs()` must switch to `resolve_all_asset_specs()`, and `deps=dg.AssetKey("upstream")` must become an iterable such as `deps=[dg.AssetKey("upstream")]`. `SourceAsset` still exists in 1.13.28 but is deprecated, not removed; prefer `AssetSpec`, using `.with_io_manager_key(...)` when needed. See the [upgrade guide](https://docs.dagster.io/migration/upgrading) and [external assets guide](https://docs.dagster.io/guides/build/assets/external-assets).

### Q54
For `type: dagster_powerbi.PowerBIWorkspaceComponent`, set `attributes.enable_semantic_model_refresh: true` in `defs.yaml` to generate executable assets that trigger and poll Power BI semantic-model refreshes.
