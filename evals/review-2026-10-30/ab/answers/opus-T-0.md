I checked every answer against the installed 1.13.28 source, and ran most of them as small experiments in `./scratch/` (a copy of the project with its own venv). `src/` and the main venv are untouched. For Q55 I installed `dagster-dbt==0.29.28` into the scratch venv only.

### Q1
`dg check yaml --validate-requirements` fails with exit code 1 and the error "`requirements.env` Component uses environment variables that are not specified in the component file: API_TOKEN". `dg check defs` passes ("All definitions loaded successfully"). That's because `{{ env.API_TOKEN }}` (`EnvScope.__getattr__`) just returns `os.environ.get(...)`, which is `None`, so the asset description becomes the literal string `"token=None"`. To get a hard failure instead, use `{{ env('API_TOKEN') }}`, which raises `ResolutionException` when the variable is unset. Also declare it under `requirements: env: [API_TOKEN]` in defs.yaml.

### Q5
You don't need `uv pip install -e .`. Entry points are registered at install time, but `uv sync` / `uv run` rebuild the editable project when pyproject.toml changes. I confirmed `dg list registry-modules` showed the new module right after `uv sync`; before syncing, dg printed a `missing_dg_plugin_module_in_manifest` warning. Once the entry point exists, `[tool.dg.project] registry_modules` is ignored completely (`EnvRegistry.from_dg_context` only reads it when `not has_registry_module_entry_point`). Only the entry point's module is used, so put everything under that module or remove the list.

### Q10
With `single_run()`, a multi-day backfill becomes one run over a partition range. Accessing `context.partition_key` then raises `DagsterInvariantViolationError: Cannot access partition_key for a partitioned run with a range of partitions. Call partition_key_range instead.` To fix it, use `context.partition_key_range`, `context.partition_keys` or `context.partition_time_window` (start/end), and return one DataFrame covering the whole range. The IO manager must also handle ranges; for example, the DB IO managers delete and insert by time window.

### Q19
Wrap the call in `with dg.partition_loading_context(effective_dt=context.scheduled_execution_time):` and inside it call `key = job.partitions_def.get_last_partition_key()`. Then return `dg.RunRequest(partition_key=key)`. In 1.13 `get_last_partition_key()` takes no arguments, so don't pass `current_time=`: it raises `TypeError: ... unexpected keyword argument 'current_time'`. Without the context it uses wall-clock "now" rather than the tick time (in my test it gave `2026-10-29` instead of `2024-02-29`). Alternatively, `dg.build_schedule_from_partitioned_job(job)` does all of this for you.

### Q23
None of the 30 historical partitions. `eager()` is `in_latest_time_window() & (newly_missing() | any_deps_updated()).since_last_handled() & ...`, so it only considers the latest daily partition. Even that one is requested only when it newly becomes missing or a dependency updates. Already-missing history is never "newly" missing. The simplest fix is a one-off backfill (UI or `dg launch --assets ... --partition-range`). To make automation cover them, use `AutomationCondition.eager().replace("in_latest_time_window", AutomationCondition.in_latest_time_window(lookback_delta=timedelta(days=31))).replace("newly_missing", AutomationCondition.missing())` (or `.without(AutomationCondition.in_latest_time_window())`).

### Q32
Subclass `ConfigurableResourceFactory[GitHub]` with a `token: str` field and `def create_resource(self, context) -> GitHub: return GitHub(self.token)`. In the asset, annotate the parameter as `github: dg.ResourceParam[GitHub]`; there is no `dg.Resource[T]` (`AttributeError`). In 1.13.28 `ConfigurableResourceFactory` is also not exported from top-level `dagster`, so import it from `dagster._config.pythonic_config`; I verified this end-to-end with `materialize`. If you'd rather avoid a private import, use a `dg.ConfigurableResource` with a `get_client()` method and annotate the asset parameter with the resource class.

### Q36
For `table_schema`, `raw_value` must be a mapping, so the list fails `check.mapping_param` with `ParameterCheckError: Param "table_schema_value" is not one of ['Mapping']`. This happens on the orchestration side, in the `PipesFileMessageReader` thread, and only shows up as a "framework exception" ENGINE_EVENT plus a "did not receive closed message" warning. The step and run still succeed, but the materialization has empty metadata. Use `raw_value={'columns': [{'name': 'id', 'type': 'int'}]}`, where columns may also carry `description`, `tags` and `constraints`.

### Q44
On a fresh machine `DagsterPlusCliConfig.write()` writes a `[cli.plus]` table to `~/.config/dg.toml`. That's `$XDG_CONFIG_HOME/dg.toml`, or `~/AppData/dg/dg.toml` on Windows, and `DG_CLI_CONFIG` overrides it. If `~/.dagster_cloud_cli/config` (or `$DAGSTER_CLOUD_CLI_CONFIG`) exists while dg.toml has no Plus settings, writes go to that legacy file instead. If both files have Plus settings, every command that loads Plus config raises `Exception: Found Dagster Plus config in both <dg.toml> and <~/.dagster_cloud_cli/config>. Please consolidate your config files.` To fix it, merge the settings into one file and delete the other.

### Q50
The usual cause is a legacy pyproject.toml with no `[build-system]` table. uv then treats the project as non-packaged: `uv sync` doesn't install it (it even uninstalled it in my test), so the entry point never reaches the environment's metadata. dg then shows only `dagster` and prints the `missing_dg_plugin_module_in_manifest` warning. Add a `[build-system]` (e.g. hatchling) or `[tool.uv] package = true` and run `uv sync` again; I confirmed `probe_proj.components` then appears. Also check that `uv run python -c "import importlib.metadata as m; print(m.entry_points(group='dagster_dg_cli.registry_modules'))"` lists it.

### Q55
The default is `"dbtf"` if `shutil.which("dbtf")` finds it on PATH, otherwise `"dbt"`. This is resolved once at import time (`DBT_EXECUTABLE`), so a Fusion `dbtf` on PATH is picked up silently. When the invocation is Fusion (`is_fusion`), `.fetch_row_counts()` logs a warning that row counts need the dbt Core adapter, which Fusion doesn't provide. It then passes the events through without row-count metadata and doesn't raise an error. `.fetch_column_metadata()` behaves the same way, and suggests the `dagster` dbt package's `log_column_level_metadata` post-hook instead. To keep Core behaviour, set `DbtCliResource(dbt_executable="dbt")`.
