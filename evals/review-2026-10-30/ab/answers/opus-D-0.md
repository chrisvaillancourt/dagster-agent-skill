### Q1
`dg check yaml --validate-requirements` fails with exit code 1 and the error "Component uses environment variables that are not specified in the component file: API_TOKEN". That check only compares the variables used in `{{ env.* }}` against the ones listed under `requirements: env: [API_TOKEN]`, and the variable doesn't need to actually be set. `dg check defs` passes ("All definitions loaded successfully."), because `{{ env.API_TOKEN }}` falls back to `os.environ.get` and returns `None` instead of raising. The asset description becomes the literal string `"token=None"` (I confirmed this in a scratch project). Use `{{ env('API_TOKEN') }}` if you want a missing variable to raise a `ResolutionException`, or `env('API_TOKEN', 'default')` to supply a default.

### Q5
You don't need `uv pip install -e .`. Entry points are registered at install time, but uv treats a `pyproject.toml` change as a reason to rebuild, so the next `uv sync` or `uv run dg ...` reinstalls the project. I tested this: `uv run dg list registry-modules` rebuilt `probe-proj` and listed the module. Once the package exposes a `dagster_dg_cli.registry_modules` entry point, `EnvRegistry.from_dg_context` ignores `[tool.dg.project].registry_modules`, which is only read when there is no entry point. The list is then redundant and can be removed.

### Q10
With `single_run()`, a multi-day backfill runs as one run over a partition range. `context.partition_key` then raises `DagsterInvariantViolationError: Cannot access partition_key for a partitioned run with a range of partitions. Call partition_key_range instead.` Even if you avoid that call, the default `UPathIOManager`/filesystem IO manager fails on output with "does not support persisting an output associated with multiple partitions". To fix it, process the whole range using `context.partition_key_range`, `context.partition_time_window` or `context.partition_keys`. Then either write the data yourself and return `None`/`dg.MaterializeResult`, or use an IO manager that handles time-window ranges (for example a DuckDB or Snowflake pandas IO manager). Otherwise, switch to `BackfillPolicy.multi_run()`.

### Q19
Pin the evaluation time to the tick, either with `with dg.partition_loading_context(effective_dt=context.scheduled_execution_time): key = job.partitions_def.get_last_partition_key()` or with `partitions_def.get_partition_keys(current_time=context.scheduled_execution_time)[-1]`. Then return `dg.RunRequest(partition_key=key)`. In 1.13, `get_last_partition_key()` no longer accepts `current_time=`: passing it raises `TypeError: ... got an unexpected keyword argument 'current_time'`. Don't rely on wall-clock `datetime.now()` either, because it breaks for late or backfilled ticks. `dg.build_schedule_from_partitioned_job(job)` does all of this for you.

### Q23
None of the 30. `AutomationCondition.eager()` is `in_latest_time_window() & (newly_missing() | any_deps_updated()).since_last_handled() & ~any_deps_missing() & ~any_deps_in_progress() & ~in_progress()`. It only considers the latest time partition (at most one request per tick), and partitions that were already missing don't count as "newly" missing. To cover history, launch a one-off backfill. Alternatively, build a custom condition, for example `dg.AutomationCondition.in_latest_time_window(lookback_delta=timedelta(days=31)) & dg.AutomationCondition.missing() & ~dg.AutomationCondition.any_deps_missing() & ~dg.AutomationCondition.in_progress()`, or use `eager().replace("in_latest_time_window", ...)`. Removing the window with `.without(in_latest_time_window())` isn't enough on its own, because `newly_missing()` still won't fire for the old partitions.

### Q32
Neither name is in the top-level 1.13.28 namespace: `dg.Resource` doesn't exist, and `ConfigurableResourceFactory` is only importable from the private module `dagster._config.pythonic_config`. With that import, `class GitHubResource(ConfigurableResourceFactory[GitHub]): token: str; def create_resource(self, context) -> GitHub: return GitHub(self.token)` works. The asset then declares `github: dg.ResourceParam[GitHub]` to receive the built client (I tested this with `dg.materialize`). If you want only public API, subclass `dg.ConfigurableResource` with `token: str` and a `get_client()` method returning `GitHub(self.token)`, and annotate the asset parameter with that resource class.

### Q36
On the orchestrator side, `metadata_value_from_external` calls `check.mapping_param` on the `table_schema` value, so a bare list raises `ParameterCheckError: Param "table_schema_value" is not one of ['Mapping']`. That error happens in the Pipes reader thread, and you get a "did not receive closed message" warning. In my test the run still reported success, but the materialization had empty metadata, so the schema is silently lost. `raw_value` must be a mapping with a `columns` key: `{'columns': [{'name': 'id', 'type': 'int'}]}`. Each column may also have `description`, `tags` and `constraints`.

### Q44
With no existing config, `DagsterPlusCliConfig.write()` writes to the dg user config file under `[cli.plus]`. That file is `$XDG_CONFIG_HOME/dg.toml`, which defaults to `~/.config/dg.toml` (`%USERPROFILE%\AppData\dg\dg.toml` on Windows), and `DG_CLI_CONFIG` overrides it. If `~/.dagster_cloud_cli/config` exists, it takes precedence and new writes go there. If both that file and `dg.toml` contain Plus settings, every `dg plus` command fails with `Exception: Found Dagster Plus config in both <dg.toml> and <~/.dagster_cloud_cli/config>. Please consolidate your config files.` `DAGSTER_CLOUD_CLI_CONFIG` overrides the path of the legacy file.

### Q50
The legacy `pyproject.toml` has no `[build-system]` table, so uv treats it as a virtual project. `uv sync` installs only its dependencies, never the project itself, so the entry point is never registered. `dg` then shows only `dagster` and warns "Your package defines a `dagster_dg_cli.registry_modules` entry point, but this module was not found in the plugin manifest". To fix it, add a `[build-system]` (for example `requires = ["hatchling"]`, `build-backend = "hatchling.build"`) or set `[tool.uv] package = true`. Then run `uv sync` again so the project is installed in editable mode with its entry-point metadata.

### Q55
`DbtCliResource.dbt_executable` defaults to `DBT_EXECUTABLE`, which is `"dbtf"` if `shutil.which("dbtf")` finds it on PATH at import time, and `"dbt"` otherwise. If the invoked executable is Fusion (`DbtCliInvocation.is_fusion`, meaning the CLI's major version is 2 or higher), `.fetch_row_counts()` doesn't fail. It logs a warning that row counts need the dbt Core adapter, which Fusion doesn't provide, and passes the events through without row-count metadata. `.fetch_column_metadata()` behaves the same way and suggests the `log_column_level_metadata` post-hook macro instead. I checked this in the dagster-dbt 0.29.28 wheel from PyPI, since it isn't installed in this project.
