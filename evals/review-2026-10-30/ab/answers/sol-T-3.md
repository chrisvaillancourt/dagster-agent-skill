### Q9
Not with default backfill settings: Dagster 1.13.28 rejects `--partition-range` unless **every selected asset** has `backfill_policy=dg.BackfillPolicy.single_run()`. With that policy, the command executes one local run covering the inclusive range, not seven partition runs. The asset and its I/O handling must support multiple partitions per run, using APIs such as `context.partition_keys`, `context.partition_key_range`, or `context.partition_time_window` rather than assuming a single `context.partition_key`. For ordinary per-partition backfills, use the Dagster UI with a running daemon instead.

### Q13
`context.definition_metadata` contains metadata on the downstream input itself, supplied through `AssetIn` or `In`; it does not contain the upstream asset’s metadata. `context.upstream_output.definition_metadata` contains the upstream output’s definition metadata, including metadata declared with `@asset(metadata=...)`, so that is where to read the table name. Despite its name, `context.upstream_output.output_metadata` does **not** expose upstream runtime metadata in `load_input`: in 1.13.28 it warns and returns `{}`. Retrieve `MaterializeResult(metadata=...)` values from stored materialization events—for example, `context.instance.get_latest_materialization_event(context.asset_key).asset_materialization.metadata`—handling missing events and filtering by partition/run when needed rather than assuming “latest” is the exact materialization being consumed.

### Q22
Register an explicit `dg.AutomationConditionSensorDefinition(name="custom_automation", target=dg.AssetSelection.assets(my_asset), use_user_code_server=True)` in `Definitions(sensors=[...])`; this executes the custom Python condition in the code server instead of requiring the daemon to reconstruct it from serialized data. Enable the sensor, or give it `default_status=dg.DefaultSensorStatus.RUNNING`, and run the daemon, such as through `uv run dg dev`. Your `evaluate(context)` must return a `dg.AutomationResult` describing the matching subset, not a boolean. User-code evaluation is Beta and limited to 500 targeted assets/checks per sensor; split larger selections, and do not assume a serialization decorator alone makes arbitrary custom code executable in the daemon.

### Q31
In 1.13.28 OSS, attach `dg.FreshnessPolicy.time_window(fail_window=timedelta(hours=24))` through the asset’s `freshness_policy=` parameter and run the Dagster daemon, for example with `uv run dg dev`. The built-in freshness daemon is enabled by default; if explicitly disabled, enable it with `freshness: {enabled: true}` in `dagster.yaml`, with no custom sensor or schedule required for evaluation. This monitors materialization recency—it does not cause materializations, so scheduling or automation is separate. The old upstream-data-lag class is now `dg.LegacyFreshnessPolicy`, accepted through `legacy_freshness_policy=`, and has different semantics.

### Q35
The effective default is `QueuedRunCoordinator`, not the class named `DefaultRunCoordinator`. Sensor-submitted runs are enqueued, and the run-queue daemon launches them subject to the default limit of **10 concurrent runs**. With no existing active runs or additional restrictions, up to 10 run concurrently while the other 15 wait and are launched as capacity becomes available. Without the daemon, queued runs are not launched.

### Q43
Run `uv run dg plus deploy start --organization <org> --deployment <deployment> --deployment-type full --git-url <repo-url> --commit-hash <sha> --yes`, then `uv run dg plus deploy build-and-push --agent-type hybrid --build-strategy docker`—or `--agent-type serverless` as appropriate—and finally `uv run dg plus deploy finish`. Configure `DAGSTER_CLOUD_API_TOKEN`, the code-location build/registry settings, and registry credentials, and preserve the same `DAGSTER_BUILD_STATEDIR` directory across CI stages. If CI builds and pushes independently, record the image using `uv run dg plus deploy set-build-output --location-name <location> --image-tag <tag>` before `finish`. Bare `uv run dg plus deploy` starts a **new end-to-end deployment**, resetting the session state and building/pushing again; it does not merely finish the existing session.

### Q48
Older examples importing `external_assets_from_specs` or calling `AssetsDefinition.from_specs(...)` fail because those APIs are absent in 1.13.28. Register `dg.AssetSpec` objects directly instead, such as `dg.Definitions(assets=[dg.AssetSpec("external_table", metadata={"table": "external_table"})])`; use `.with_io_manager_key("table_io")` when downstream inputs need an I/O manager to load the external data. `dg.SourceAsset` still exists but is deprecated in favor of `AssetSpec`—it has not been removed in 1.13. The `@dg.observable_source_asset` and `@dg.multi_observable_source_asset` decorators also still exist, so do not treat those observation APIs as removed.
