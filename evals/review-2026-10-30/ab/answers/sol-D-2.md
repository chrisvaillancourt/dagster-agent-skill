### Q3
Final kinds are `{b}`, not `{a, b}`; user tags merge to `{'x': '1', 'y': '2'}`, and the actual tags also contain `{'dagster/kind/b': ''}`. The default post-processing operation is `merge`, but it merges only tags and metadata; kinds are replaced. `uv run dg check yaml` validates the outer `post_processing` keys and that `assets` is an array of objects, but **does not validate the nested processor/attribute keys**; those are validated when definitions load.

### Q7
As written, it raises `TypeError` because `Definitions.map_asset_specs` requires the keyword-only argument `func`. Use `defs.map_asset_specs(func=lambda spec: spec.replace_attributes(partitions_def=pdef))`; in 1.13.28 this can update an executable asset’s partitions definition inside `Component.build_defs`. ### Q12
The I/O manager attempts to load all 24 mapped hourly partitions and fails on a missing file, so the downstream asset body does not run. To permit partial input, set `ins={"up": dg.AssetIn(metadata={"allow_missing_partitions": True})}` on the downstream asset; it then receives a dictionary containing the three available partitions, with missing partitions omitted. `TimeWindowPartitionMapping(allow_nonexistent_upstream_partitions=True)` is not the fix for missing stored data: it concerns partitions outside the upstream partition definition.

### Q21
For cron-defined cycles, use `dg.AutomationCondition.on_cron(cron_schedule)`, which waits for all upstream dependencies to update since the latest cron tick; its underlying predicate is `all_deps_updated_since_cron(cron_schedule)`. The common wrong choice is `dg.AutomationCondition.eager()`: it responds to **any** upstream update once its other readiness conditions hold, rather than requiring a fresh update from every upstream. Define the cycle boundary explicitly—`on_cron()` does not mean “since the downstream last materialized” ([reference](https://docs.dagster.io/guides/automate/declarative-automation/automation-condition-reference)).

### Q29
With `orders`, its blocking check, and downstream selected, `passed=False` defaults to `AssetCheckSeverity.ERROR`: `orders` materializes, the check fails, and downstream does not execute. `dg.materialize(...)` defaults to `raise_on_error=True`, so it raises `DagsterAssetCheckFailedError`; with `raise_on_error=False`, it instead returns an unsuccessful result. A failed blocking check with `severity=dg.AssetCheckSeverity.WARN` records the failed evaluation but allows downstream to execute and, absent other failures, returns a successful result. If both checks are present, the ERROR failure still blocks downstream.

### Q34
Set `DG_PROJECT_PYTHON_EXECUTABLE=../.venvs/my-project/bin/python` in the **project root’s `.env` file**, pointing to the Python executable rather than the virtualenv directory. Relative paths resolve against the project root. Exporting it in your shell alone does **not** work: `dg` reads this override directly from `.env`, not from the process environment ([configuration reference](https://docs.dagster.io/api/clis/dg-cli/dg-cli-configuration#using-a-custom-python-executable)).

### Q39
No: `pool="db"` does not throttle unless an explicit pool limit or `concurrency.pools.default_limit` supplies a limit. Normal step completion/failure cleanup releases claimed slots, but merely marking a run `CANCELED` does not guarantee release of an orphaned slot. For automatic recovery, run the Dagster daemon with run monitoring enabled and configure a positive `run_monitoring.free_slots_after_run_end_seconds`; a subsequent monitoring iteration frees slots belonging to finished runs after that grace period. This cleanup timeout is unset by default; stale slots can also be freed manually through the UI ([reference](https://docs.dagster.io/deployment/execution/run-monitoring#freeing-concurrency-slots-after-run-completion)).

### Q47
`@asset(freshness_policy=LegacyFreshnessPolicy(...))` raises `ParameterCheckError`: `freshness_policy` expects the new `FreshnessPolicy`, not `LegacyFreshnessPolicy`. `AssetOut(legacy_freshness_policy=...)` is still accepted and stored in 1.13.28 through a hidden compatibility parameter—it was not actually removed from the implementation. `@observable_source_asset(auto_observe_interval_minutes=10)` is accepted at runtime but silently ignored, leaving the interval `None`. Migrate to `FreshnessPolicy.time_window(fail_window=timedelta(minutes=5))` and an observation `automation_condition` such as `AutomationCondition.on_cron("*/10 * * * *")`, noting that these are not exact semantic equivalents of legacy lag policies or elapsed-time intervals.
